# Native H.264 diagnostic plan

Continue the approved native pipeline experiment without changing the application
or frontend. Use only the owned synthetic fixture; do not enumerate user windows.

1. Preserve the capture-only command and add an explicit, non-overwriting output
   option. Create a private MP4 diagnostic, not a WebRTC integration.
2. Convert the final owned BGRA texture to 640x360 NV12 with D3D11 video processing.
   Submit repeated immutable GPU samples to a Media Foundation sink writer.
3. Record GPU input and hardware-transform permission separately from actual
   encoder identification. Do not infer hardware execution from configuration.
4. Independently count/decode H.264 frames with installed FFprobe/FFmpeg, check
   the synthetic color, and reject incorrect codec, size, timing or empty output.
5. Run regression tests, formatting, Clippy, dependency and repository checks.
   Document observed failures and evidence limits. Keep all output ignored.

The repeated final texture validates format/resource interoperability. It does
not measure a live capture/encode queue, GPU latency, native RTP packetization,
congestion control, audio synchronization or official-viewer compatibility.

lifecycle and missing color metadata problems. The same checker subsequently

## Follow-up: encoder identification (2026-11-12)

Completed the first half of the next gate. `inspect_encoder` walks the sink
writer chain (`IMFSinkWriterEx::GetTransformForStream`) and classifies the first
video-encoder MFT by `MFT_ENUM_HARDWARE_URL_Attribute`. A unit test covers the
classification; the validator now rejects reports without a known
`encoder_kind`. Three consecutive independent FFprobe/FFmpeg-verified runs on
the development workstation reported `hardware`. Vendor/adapter names are not
emitted. Remaining: bounded elementary access-unit output for RTP, live frame
recycling, adapter attribution on multi-GPU systems, and official-viewer decode.
